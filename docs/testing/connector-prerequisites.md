# Read-only connector prerequisites and planner contract

Research date: 2026-10-07. This is feasibility/configuration evidence and a contract recommendation, **not implementation or live-provider verification**. Only public official documentation and local configuration presence/metadata were inspected. No private mail/course/calendar data was read, no browser automation was used, and no OAuth registration, consent, provider write, dependency installation, billing action, or paid request occurred.

## Product and existing architecture boundary

The requested direction is a connector-driven planner: after source-specific user consent, automatically import and display **internal suggestions** with a short description, action, due/scheduled date, source, and details. Automatic internal display is not external Calendar creation or Canvas submission/completion. Outlook and Canvas are candidate sources ("maybe including"), not a promise that either is connected. Do not add functional-looking connection controls for unavailable integrations.

The inspected `EXECUTION_PLAN.md`, `docs/adr/003-browser-oauth.md`, `docs/adr/004-p0-processing.md`, and `docs/architecture/api-contract.md` describe the prior Gmail-centered architecture and explicit task/calendar approval. The main integration owner is responsible for reconciling the planner pivot in those files. Preserve server-owned sessions, encrypted provider tokens, per-user ownership, bounded imports, verified text evidence, disconnect retention fencing, and the explicit external-calendar confirmation boundary. Canvas stays read-only unless the user separately explicitly confirms a specific write; even toggling a Canvas planner override is a provider write. No Canvas browser automation is permitted.

Source inspection at research time found only Google configuration in `services/api/src/config.ts`, Google-specific connection/request boundaries in `services/api/src/auth/google.ts`, and Gmail-specific persisted identity in the original email architecture. A new provider requires a real backend adapter, OAuth/callback lifecycle, account-scoped identity/storage, and contract tests; a configured tool session is not app OAuth integration.

## Local discovery: what is actually available

Presence-only inspection of `.env` and `.env.google-web` found nonempty Google client ID, client secret, redirect URI, and allowed-user configuration. No Microsoft/Entra/Azure/Outlook/Canvas configuration keys were found there, in `.env.example`, or among matching process-environment variable names. `.omp/mcp.json` names only `google-workspace`. No secret values were printed, copied into this document, or sought in unrelated machine stores. This bounded discovery does not prove an account owner has no existing registration elsewhere.

The user's successful Gmail connection is ground truth; it was not re-tested here. Existing project evidence describes enabled Gmail/Calendar APIs and an approved Google Web client. Gmail/Google Calendar are therefore the only discovered configured provider path, not a newly enabled connector. Live access still depends on the user's grant and its current validity. AI extraction is disabled in the stated local setup; a credential's presence does not authorize paid API use. The one-case subscription experiment in `subscription-experiment.md` is not a backend extractor or app subscription integration.

**No additional fully reachable Outlook or Canvas integration can currently be enabled without missing client configuration and owner/institution decisions.** No real-provider request was made to work around these prerequisites.

## Microsoft Outlook through Graph

### Prerequisites and consent

Use delegated authorization-code OAuth with a backend-owned confidential Web client, state/browser binding and PKCE; never application-wide mailbox permission for this planner. Official [registration instructions](https://learn.microsoft.com/en-us/graph/auth-register-app-v2) require a Microsoft Entra tenant and appropriate registration authority, distinguish **Application (client) ID** from Object ID, and describe Web redirect configuration and confidential-client credentials. The account owner must identify an approved existing registration/tenant (or separately authorize its creation), choose the supported account audience, supply its client ID plus server credential securely, and approve the exact callback. Do not silently choose a multi-tenant/public audience.

[Delegated access documentation](https://learn.microsoft.com/en-us/graph/auth-v2-user) describes authorization, code exchange, consent and `offline_access` refresh tokens. Choose a tenant-specific authority for a single organization; `organizations`, `consumers`, and `common` have different account audiences and must agree with registration. Request only identity scopes needed by the chosen sign-in design, `offline_access` for consented continued import, and the independently selected mail/calendar read scopes. A backend Web secret/certificate must never reach browser code. OAuth token exchange/refresh is distinct from a content write, but neither was attempted in this research.

The [permission reference](https://learn.microsoft.com/en-us/graph/permissions-reference) documents:

- `Mail.ReadBasic`: basic mail excluding body/preview body, attachments and extended properties. It is insufficient for body-based action extraction/details. Use delegated `Mail.Read` when the user agrees to mail-body import.
- `Calendars.ReadBasic`: basic events excluding properties such as body, attachments and extensions. Prefer it for a title/time-only view; use delegated `Calendars.Read` if event body/details are part of the consented feature.
- These delegated read scopes support work/school and personal Microsoft accounts and list `AdminConsentRequired: No`. This is **not a guarantee** an institution permits user consent: tenant consent/access policy may still require administrator approval. No `Mail.ReadWrite`, `Mail.Send`, or `Calendars.ReadWrite` is needed for import.

Testing requires a supported Outlook.com mailbox or an approved organizational mailbox with the relevant service available; an Entra identity alone does not establish mailbox access. An isolated Microsoft 365 development tenant is optional, not something this project already has. The official [Developer Program FAQ](https://learn.microsoft.com/en-us/office/developer-program/microsoft-365-developer-program-faq) limits E5 sandboxes to qualifying members (for example eligible Visual Studio subscriptions, qualifying partner programs, or support customers); ordinary membership/enterprise subscription does not automatically provide one. Do not promise a free sandbox, create an account, start a trial, or purchase a license.

### Read endpoints and native fields

- [List messages](https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0): `GET /v1.0/me/messages` or an explicitly selected mailbox folder. Use bounded date windows and `$select`; follow validated Graph `@odata.nextLink` URLs without inventing skip offsets. Fetch no attachments. [Message fields](https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0) include `subject`, `body`/`bodyPreview`, sender, `receivedDateTime`, `webLink`, and `flag`. Request `Prefer: IdType="ImmutableId"` for stable message identity across folder moves within its supported scope; always include connected-account identity in the local key.
- [Follow-up flag](https://learn.microsoft.com/en-us/graph/api/resources/followupflag?view=graph-rest-1.0): `flagStatus`, `dueDateTime`, `startDateTime`, `completedDateTime`. A present valid `dueDateTime` is a **native follow-up deadline**, not proof of the sender's requested deadline. A normal message has no generic structured body deadline. Received/sent time and importance are not due dates or proof an action is required.
- [Calendar view](https://learn.microsoft.com/en-us/graph/api/calendar-list-calendarview?view=graph-rest-1.0): `GET /v1.0/me/calendar/calendarView?startDateTime=…&endDateTime=…` expands single events, recurring occurrences, and exceptions in a bounded window. [Event fields](https://learn.microsoft.com/en-us/graph/api/resources/event?view=graph-rest-1.0) provide `subject`, `bodyPreview`/`body`, `start`, `end`, `isAllDay`, `isCancelled`, `type`, `seriesMasterId`, and `webLink`. Keep recurrence occurrences distinct and remove/mark cancellations in a complete successful reconciliation. Start/end are **event times**, not task deadlines; no AI is needed to place an existing event on an internal calendar. Preserve timezone/all-day semantics rather than converting every item into a timed task.

## Canvas

### Prerequisites and exact read scopes

Official [OAuth overview](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth) requires a Canvas API OAuth client ID and secret. For hosted Canvas, these developer keys come from the institution's administrator. [Developer-key documentation](https://developerdocs.instructure.com/services/canvas/oauth2/file.developer_keys) states that institution keys work only in that root account/subaccounts; global keys require Instructure and must be enabled by each account. A student's existing browser sign-in cannot supply this application prerequisite. An LTI key is not a substitute for ordinary user-delegated Canvas REST OAuth.

Missing locally: the institution-approved HTTPS Canvas origin, an enabled scoped API developer key/client ID and secret, registered redirect URI, approved test user/course access, and institution permission for the requested scopes. No host was guessed and no private course content was inspected. A future adapter must pin the approved origin and API paths, reject credential-bearing redirects/cross-host pagination, and never send tokens to arbitrary URLs supplied by course content.

Recommended minimal read scope selection (enable only endpoints the adapter actually calls):

- Current user's planner feed: `url:GET|/api/v1/planner/items`
- User's active courses for course labels/assignment discovery: `url:GET|/api/v1/courses`
- Course assignments including undated assignments: `url:GET|/api/v1/courses/:course_id/assignments`
- Assignment details when not already included: `url:GET|/api/v1/courses/:course_id/assignments/:id`
- Separate planner-note listing, only if needed: `url:GET|/api/v1/planner_notes`

Endpoint evidence: [courses](https://developerdocs.instructure.com/services/canvas/resources/courses), [assignments](https://developerdocs.instructure.com/services/canvas/resources/assignments), [planner](https://developerdocs.instructure.com/services/canvas/resources/planner). Scope strings encode the literal documented route template, not a concrete course ID. Requested scopes must be a subset of the key's administrator-approved scopes; scoping does not grant a user access to otherwise inaccessible courses. Request no submission, grade, planner-note, or planner-override write scopes. The key's **Allow Include Parameters** setting controls whether scoped calls honor `include`/`includes`; do not depend silently on `include[]=submission` for completion status.

Canvas OAuth access tokens normally expire after one hour and use a refresh token; keep both server-side encrypted and handle revocation/changed scope as reconnect-required. Never solicit manually generated personal tokens as a multi-user onboarding shortcut: the official OAuth overview says applications used by multiple users must use OAuth and asking other users to generate/paste tokens violates Canvas API policy. No manual token was created here. Any eventual provider-side revocation is an explicit disconnect action requiring the applicable user confirmation; this research performed no such call.

The Assignment object explicitly documents `due_at` as the date applying to the requesting user when overrides exist. Do not select the earliest/default date from `all_dates`, nor replace a null effective due date with another student's date. A dated planner feed is not proof that all undated assignments have been imported; fetch the consented assignment collection if the product promises those items. Follow bounded, same-origin pagination and disclose incomplete/truncated coverage.

Completion/visibility fields have separate meanings: `planner_override.marked_complete` is user-set planner completion, `dismissed` is visibility, and `submissions` contains source submission status. They are not interchangeable with local approval or grading. `has_submitted_submissions` means at least one student submitted, **not** that the current user completed the assignment. Import these facts read-only; never update Canvas to match a local planner click.

## Recommended normalized planner contract

This is a recommendation, not a claim these fields or connectors are implemented.

- Identity: `provider`, connected-account/tenant-or-Canvas-origin identity, `sourceType`, `sourceId`, optional course/calendar/occurrence identity. Deduplicate by these stable identities, not title/date; never collapse two accounts' matching IDs.
- Presentation: `title`, bounded plain-text `description`, nullable `action`, `actionOrigin` (`provider_native`, `template`, `verified_extraction`, `user`), source label/link, fetch timestamp and details reference. Provider HTML/content is untrusted; do not render executable HTML or invent an AI summary while extraction is disabled.
- Dates: semantic kind (`deadline`, `follow_up`, `event`, `planner_note`), precision (`instant`, `date_only`, `missing`, `uncertain`), nullable exact due instant/date-only value, independent event start/end/all-day fields, source timezone, provenance (`provider_native`, `verified_extraction`, `user`), source field path and original value. Native structured dates bypass AI extraction; keep evidence as source-field provenance rather than fabricated body quotes.
- Uncertainty: distinguish "No source due date" from "Date needs review" and "Extraction unavailable". Keep date-only as date-only; do not invent midnight, end-of-day, year, timezone, or duration. Unsupported timezone/date conversion remains visibly uncertain. Never schedule undated mail on its received date as if that were a deadline. A calendar can show dated items while retaining an undated/review list.
- Mail extraction: without an exact native follow-up field, body-derived action/deadline requires validated extraction and separate supporting quotations under the existing evidence rules. Import success alone cannot claim the email was understood. Preserve user edits/review decisions when source data refreshes and disclose changed source facts separately.
- Consent and side effects: consent to import permits bounded automatic internal suggestion display, not external calendar event creation, notification delivery, email replies, task submission, or source completion writes. External-calendar creation remains a separate explicit confirmed action. Canvas writes remain disabled absent separate explicit user approval.

## Connector health and acceptance checks

Separate states instead of one ambiguous "sync failed" label:

1. Configuration/capability: implemented and configured versus unavailable/missing owner prerequisites. Do not expose a fake working connect action.
2. Authorization: disconnected, connected with granted capabilities, reconnect required, or institution consent blocked.
3. Import: idle/running/succeeded/partial/failed; imported count, coverage window/limit, last attempt, last successful import and safe retryable error.
4. Interpretation: native mapping ready, extraction disabled/not configured, extraction queued/running/succeeded/failed, or no supported action. AI failure must not erase readable imported data or misreport working OAuth/import as broken. Conversely, imported message counts are not extracted-action counts.

Preserve last-success data with a stale/partial marker during provider failure. Use safe errors without tokens, OAuth URLs/codes, raw provider bodies, course content, or mail text. Reconnect/disconnect must fence stale workers so old responses cannot recreate purged records.

Recommended central acceptance coverage before enabling a new source: source-specific consent and denied scopes; expiry/reconnect; cross-user/account isolation; pagination/truncation and idempotence; preserved user decisions; source deletion/cancellation; Canvas effective override/null due/lock-vs-due distinction; Canvas unavailable includes and other-student submission trap; Outlook missing follow-up due, moved-message identity, recurring exceptions/cancellations, all-day/timezone conversion; malicious HTML/links; AI disabled with successful import; stale snapshot after import failure; and zero external writes during import/automatic display. Start with local synthetic provider fixtures; live read-only testing waits for approved credentials and user consent. No builds, tests, linters, formatters, or live-provider verification were run in this research slice.
